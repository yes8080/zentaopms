## 字段去向

| 字段 | 反馈行为 | 转单行为 |
| --- | --- | --- |
| 产品、平台／分支、模块 | 选择后校验产品归属，附加分支分别保存模块。 | 单张原生需求预填主选分支和模块。 |
| 类别、优先级、来源、关键词、预计工时 | 原生枚举或输入规则，随反馈修订保存。 | 在支持这些字段的原生需求表单预填。 |
| 标题、描述与验收标准 | 标题与两个编辑区独立保存，文本和图片可随修订回显。 | 单条转单预填标题和最新正文，三类需求另带入验收文字。内嵌图片保留在原反馈。 |
| 客户、渠道、来源备注 | 反馈业务信息，按反馈权限查看。 | 保留在原反馈。 |
| 附件 | 反馈详情上传、下载和移除，下载校验反馈权限。 | 由操作者在目标表单单独确认。 |
| 下一步、剩余事项与对客答复 | 需求池办理历史和状态流转。 | 原生目标的研发进度与反馈独立记录。 |

## 普通角色办理验收

在禅道 22.7 测试实例使用两个非管理员测试账号，分别配置为产品经理和客服。两者使用同一个授予需求池列表及详情访问的测试权限组。

| 场景 | 预期及实测结果 |
| --- | --- |
| 产品经理代录 | 相同操作提交两次返回同一反馈编号，反馈出现在「我提交的」。负责人是客服，产品经理在转交前不能开始办理。 |
| 客服直接结案 | 反馈出现在「待我处理」和地盘。客服填写配置已修正的处理结果后关闭，未创建承接单。 |
| 客服转交 | 另一条反馈转交产品经理后，从客服的「待我处理」退出，出现在产品经理的「待我处理」。 |
| 私有产品 | 两个账号均看不到私有产品或其反馈。直接访问受限反馈及附件均返回 HTTP 404。 |

进度核对服务的停启、目标删除及恢复已在独立 Compose 实例验证，过程见插件 README。

| 权限场景 | 实测结果 |
| --- | --- |
| 可读反馈，未授予原生查看权限 | 反馈详情不显示关联的研发需求、用户需求、业务需求、Bug 和任务链接。 |
| 已授予两侧查看权限 | 五类原生单据均显示来源反馈反链。任务还要求拥有对应执行的访问权限。 |
| 可查看原生单据，撤销需求池详情权限 | 五类原生详情均不显示来源反馈链接或标题。 |
| 私有反馈内嵌图片 | 管理员可在反馈详情读取内嵌 PNG。普通账号访问该详情返回 HTTP 404。 |

## 多客户共用需求验收

在禅道 22.7 测试实例，以管理员合并反馈 #530、#531、#532，新建研发需求 #112。重复提交返回相同需求编号。随后将反馈 #533 关联到原需求，四条反馈均可双向打开。页面和数据库确认四条承接关系均指向研发需求 #112。

| 反馈编号 | 实际结果 |
| --- | --- |
| 530 | 甲确认仓库库存导出，记录电话答复并关闭。 |
| 531 | 乙尚未升级，保留跟进中及等待升级的下一步。 |
| 532 | 丙的审批人列仍未处理，保留跟进中及剩余事项。 |
| 533 | 第四位客户关联已有需求，保留跟进中。 |

四条详情分别保留自己的办理记录。此用例已加入 `tests/smoke.py` 的批量转单验收。

## 产品负责人变更验收

在禅道 22.7 测试实例，原生产品 #37 初始配置客服账号为需求池负责人。切换预览接口的产品参数可分别取得已配置和待配置结果。反馈 #544 先按原配置分给客服。打开第二份提报表单后，在原生产品编辑页将负责人改为管理员，随后提交得到反馈 #545，分派给管理员。清除配置后，新件显示待配置。分别重试原提交，两个既有编号和实际负责人均保持原值。

## 原生状态回写验收

在禅道 22.7 测试实例，以管理员从原生入口关闭研发需求 #113、用户需求 #114、业务需求 #115，将 Bug #26 标为已解决并记录「已修复」，取消并关闭任务 #25。手动运行与定时核对使用的同一命令后，数据库记录三种需求的关闭状态、阶段和原因，Bug 的已解决状态及解决方案，以及任务的关闭状态及取消原因。来源反馈 #549、#550、#551、#552、#560 均保持跟进中。任务反馈详情显示「已关闭」和「已取消」。

0.21.0 在测试实例通过原生操作重新激活上述五类单据。未调用定时核对命令时，三类需求和 Bug 的快照自动更新为 active，任务更新为 doing，五条反馈仍为 tracking。随后验证手动核对命令可继续运行，完整冒烟测试通过。

## 并发转单验收

两个独立的管理员登录会话同时从反馈 #617 提交原生研发需求。两个请求均成功并返回 #125。数据库核实只生成一张原生需求、一条承接关系，反馈只增加一个版本并进入跟进中。此用例已加入 `tests/smoke.py` 的研发需求转单验收。

## 任务承接恢复验收

在禅道 22.7 测试实例，创建原生任务 #30，并用测试数据模拟反馈 #663 的转单在原生任务提交后中断。只有预留标记时，重新提交提示待核对，数据库中仍只有一张任务。将已核实的原生任务编号写入测试操作记录后，再次提交成功补齐承接关系。重复提交仍返回 #30，数据库确认关系数为一。

## 所属计划验收

禅道 22.7 的反馈 #689 保存了所属计划 #4。列表内提报表单的预览接口按产品和主选分支返回计划，服务器拒绝其他产品及分支的计划编号。反馈编辑页能回显已选计划，打开原生研发需求转单表单时带入计划。删除测试计划后，修改反馈正文仍保留历史计划编号，转单链接不再携带该计划。

## 抄送字段验收

禅道 22.7 的反馈 #711 提交时选择两个有效账号，其中一个重复提交。保存后名单去重，原生研发需求表单预填两个账号。提交不存在的账号时，服务器拒绝。该检查已加入 `tests/smoke.py` 的原生产品和研发需求转单组合。

## 单条转单正文验收

禅道 22.7 完整冒烟测试通过。五类原生表单均预填反馈正文。另用含 PNG 的富文本反馈确认，研发需求表单带入最新修订的格式化正文和独立验收文字，原反馈仍保留 PNG。批量转单表单未汇集来源正文。

## 校验失败回显验收

新建和编辑反馈时均使用含格式文本和内嵌 PNG 的样本，提交无效预计工时。新建表单保留操作编号，编辑表单展开并保留未保存的客户信息、正文和图片。再次打开详情仍显示已保存的记录。修正工时后使用原表单版本成功保存。此用例已加入完整冒烟测试。

## 客户使用版本验收

禅道 22.7 完整冒烟测试覆盖客户使用版本的提报、详情显示、修改和长度校验。转单表单继续使用原生目标的版本规则，客户使用版本留在原反馈供跟进。

## 分支和平台阶段验收

在禅道 22.7 对多分支反馈 #494 和多平台反馈 #495 执行原生发布关联。发布 #2 和 #3 分别仅覆盖各产品的 Matrix A。两条反馈的承接区域均显示 Matrix A 已发布，Matrix B 依然缺少阶段记录，反馈均保持跟进中。

## 负责人失权和恢复验收

在禅道 22.7 测试实例，将产品 #47 配置给客服账号。反馈 #825 按配置分派。打开下一份表单后撤销客服账号的需求池详情权限，预览立即显示待配置。提交得到 #826，标记待配置并由提报人临时跟进。恢复权限后，预览恢复已配置，反馈 #828 分给客服。既有反馈及重试均保留原编号和原分派结果。

## 状态历史验收

Chromium 验证在详情开始跟进后，原生历史组件展示经办人和办理动作。已有关闭及重开记录沿用插件数据，状态历史仍由反馈详情的读取权限保护。

## 三类批量转需求复验

同一次禅道 22.7 完整冒烟测试逐一执行研发、用户、业务需求的批量转单，生成目标 #168、#169、#170。每类均以三条同产品反馈新建一个目标，再关联第四条。重复提交返回原编号，源版本变化或混选产品时拒绝整批操作。四条反馈的客户答复和结案结果分别保存。另在独立的用户需求 #162、业务需求 #164 用例中，通过数据库确认每张目标恰有四条承接关系。
