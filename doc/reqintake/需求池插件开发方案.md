# 需求池插件开发方案

目标版本为禅道开源版 22.7，开发基线采用历史选定的 docker-baseline@4f9fbe9c，部署环境为 PHP-FPM、Nginx、MySQL 8.4。方案采用 GPT-6.2 Astra，后续实施工作包使用 GPT-6.2 Sol / low。下述检查属于待执行的开发验收要求。

## 一、先建立原生对照基线

在干净的开源版 22.7 安装实例中，准备普通、多平台、多分支三个产品样本。使用同一账号、语言、主题、视窗和样本数据，采集原生研发需求列表、新建、编辑、详情四组基准图。另采集原生产品新建、编辑、详情，确定「需求池负责人」扩展位置。

源码优先核对 module/product/ui/browse.html.php、module/story/ui/create.html.php、module/story/ui/edit.html.php、module/story/ui/view.html.php 及相应的表单配置、语言、模型和文件组件。页面字段是否出现、能否多选及默认值以基线实际配置为准。

字段对照表最少记录：原生名称、所属页面、字段含义、控件、显示条件、必填与默认值、数据来源、存储、编辑回显、转单映射、截图。每项注明「原生复用」「反馈业务差异」或「由原生目标提供」及理由。前端复用 ZIN 组件和原生布局。

## 二、插件及产品配置

以 reqintake 为独立模块，按开源版标准插件方式交付。插件登记全局一级导航、列表和详情路由、权限、历史语言、对象类型及地盘待办。采用插件自己的表和扩展文件，不依赖企业版模块。

在产品新建／编辑表单扩展单人账号选择器「需求池负责人」，在产品详情基本信息区显示。配置按 productID 唯一保存账号。校验操作者的产品维护权限，以及候选账号是否有效并具备该产品的反馈办理权限。创建产品时先取得真实产品 ID；配置保存失败须明确提示，可从编辑页补配。

**负责人解析只实现一份，供创建表单和服务端保存共同调用。**

| 调用时点 | 输入、输出与约束 |
|---|---|
| 用户选择或切换产品 | 输入有权提报的 productID，返回该产品有效负责人的账号与显示名，或待配置标记。切换 A 到 B 后忽略迟到的 A 请求结果。 |
| 提交新反馈 | 再次校验最终产品并读取有效配置，把实际经办账号及分配依据写入反馈。客户端显示值仅用于预览。 |
| 产品无有效负责人 | 返回待配置标记，按产品设计由提报人临时跟进。配置异常可筛选、可转交，临时跟进不赋予额外权限。 |
| 修改配置或重试提交 | 产品配置修改只作用于以后的新件。相同创建操作重试返回原反馈和其实际经办人。 |
| 停用及重新启用 | 隐藏产品扩展字段，保留配置与历史。重新启用后校验账号资格。 |

这是需求池创建流程内的调用。未来外部系统写入可复用同一分派规则；本期不需要开放飞书接口。

## 三、数据、原生字段与权限

| 对象 | 保存和复用原则 |
|---|---|
| 反馈 | 保存产品、原型中的可编辑业务字段、客户或来源线索、渠道、提报人、一个当前负责人、三态、下一步、剩余事项、关闭原因和更新版本。按产品、负责人、状态和业务更新时间支持查询。 |
| 产品范围与模块 | 保留平台／分支及模块的真实 ID 和归属。依据 22.7 原生选择粒度验证单值、多值及模块关联，避免把多个范围压成一串显示名。服务端复核产品、分支、模块、计划的一致性。 |
| 原生枚举和账号字段 | 类别、优先级、来源、来源备注、关键词、抄送、预计工时沿用原生选项和格式。已停用历史值应能识别，编辑无关字段时应保留原值。 |
| 正文及附件 | 描述与验收标准分别使用原生富文本控件，独立保存。绑定内嵌图片、临时上传及普通附件；检查保存、再编辑、预览、下载和移除。文件和图片读取均校验对象权限。 |
| 承接关系 | 按反馈 ID、目标类型、目标 ID 唯一，建立按目标反查索引。记录承接范围、新建或关联方式、目标进度摘要及最近核实时间。 |
| 历史与转单操作 | 复用原生 action/history 显示办理及字段变化。实际对客答复记录对象、渠道、时间、经办人和内容。转单另用唯一操作编号记录来源集合、目标类型、实际目标和核对状态。 |

服务端统一执行状态规则：新件待评估，开始办理或成功承接后跟进中，按本反馈的结果关闭，重开回跟进中。办理、转交和结案校验权限及记录版本。列表先限定可见范围再分页计数；详情、搜索、关联选择、来源反链和附件各自鉴权。详情可见性不随关联关系扩大。

## 四、原生转单与字段带入

单条支持五类目标。业务需求、用户需求、研发需求分别检查 epic、requirement、story 的原生入口与站点层级开关；Bug 核对影响版本等必填项；任务先选择有权且与产品关联的执行。目标自己的评审、分派、版本和状态流转均在其原生页面办理。

单条从兼容字段预填产品、平台／分支、模块、类别、标题、描述和验收标准。在原型中可编辑的层级、父需求、评审选项允许作为转单建议，在目标表单确认。计划与客户适用版本、需求版本分别处理。

列表批量只接收同产品反馈，一次创建或关联一张三类需求中的目标。先校验每个来源、目标层级和操作权限。共同字段一致时可预填；不同分支、模块、类别或描述由操作者确认。明确展示每条反馈承接的范围。客户私有原文、附件和图片不自动汇集；明确选用时验证源读、目标写和文件归属。关联已有单据只增加关系，保留该目标的原有正文与来源。

**防止重复造单。** 同一操作沿用一个编号。先在基线实测各原生入口的实际提交边界，验证能否在创建目标时可靠保存操作标识及真实目标 ID。目标已建但部分关系未写入时，凭持久记录找回目标，幂等补齐关联。结果不明时转待核对并阻止盲目重建，不按标题或最新 ID 推测。取消表单、校验失败均不提前流转反馈。批量界面须保证一次只产生一张目标，原生可能产生多张的模式需在提交前限制或明确处理。

## 五、进度回写

以原生单据为研发进度的数据源。可用的保存事件触发更新，另设一项可重启的定时核对，覆盖漏事件、批量操作和容器重启。两条路径共用同一重算逻辑，只扫描已建立承接关系的目标。

需求读取真实状态、阶段及关闭原因，Bug 读取状态和解决方案，任务读取状态及完成或取消结果。按目标反查来源反馈，同一事实只更新一次业务进展。单分支发布仅影响适用范围。原生目标取消、删除或重开时保留历史并提示复核；同一对象恢复后复用原关系。读取失败展示最近成功核实时间。

同步只更新承接进度。客户实际答复、剩余事项及本反馈的关闭均走各自的办理操作。原生详情可按权限反查来源，反馈详情也能打开有权查看的目标。

## 六、实施包与发布验收

| 工作包 | 完成条件 |
|---|---|
| A 原生基线 | 安装最小标准插件，验证一级导航、产品字段扩展、地盘、文件访问、调度及真实目标编号。交原生页面截图、字段对照表和五类目标接入结论。 |
| B 提报与办理 | 交付负责人配置及创建调用、跨产品列表、原生字段、直接办理、三态、沟通历史与转交。跑通客服和产品经理现场提报。 |
| C 转单与回写 | 交付单条五类、批量三类、关联已有单、部分承接、双向查看、自动回写与失败恢复。 |
| D 发布 | 同一版本交付源码、标准插件 ZIP、校验和、Compose 安装升级回退说明及实测报告。验证非默认表前缀、备份、升级、停用和重装，以及 PHP 和 Nginx 容器重建后的代码、静态资源与上传文件。 |

发布前必须用真实页面和数据库结果验收：

1. **字段与界面。** 普通、多平台、多分支产品分别跑列表、新建、编辑、详情。对照原生截图核验字段顺序、树状模块、多值回显、类别与优先级、两个富文本区域、内嵌图片、附件、两栏及底部浮动工具栏。校验失败不丢输入。
2. **产品分派。** 在 A、B 上分别配置负责人；切换产品时界面正确联动。用户打开表单后修改 B 的配置，再提交时按最新有效配置分派。另验未配置、失权、停用、重新启用以及既有反馈不被改派。
3. **收件与直接办理。** 产品经理现场代录仅生成一份待评估反馈。客服改配置可零转单结案。转交后分别从「我提交的」「待我处理」查到正确记录。
4. **五类转单。** 各创建或关联原生目标，核实真实编号、类型、权限、双向链接及一次实际状态变化。已有目标的原始来源和正文保持可追溯。
5. **多人同需。** 三份来源建一张需求，第四份关联已有。甲已确认、乙未升级、丙有额外事项时，三份反馈分别显示正确进展和结论。
6. **并发、恢复与权限。** 重复点击、响应丢失、目标已建但关联未全、目标删除后恢复、调度停止再启动。核对目标数、关系数和状态。受限账号不能通过反链、附件或内嵌图片读取无权内容。

测试报告应记录实例版本、角色、反馈与目标编号、截图、预期、实际及未通过项。原生字段对照和负责人分派都是首版验收项。
