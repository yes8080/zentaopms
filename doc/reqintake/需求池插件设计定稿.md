# 需求池插件设计定稿

适用版本为禅道开源版 22.7。内部模块名为「需求池」，对外可称「许愿池」。

## 一、定位与入口

需求池汇总所有产品收到的用户需求反馈。客服接到电话、产品经理拜访客户、实施人员收到现场反馈，都可以用自己的禅道账号代为登记。客户是提出者，登录员工是提报人，两者分别记录。

从全局一级导航打开「需求池」，首页就是需求池列表，默认汇总本人有权查看的各产品反馈。点击「提交需求」，在新建表单中主动选择所属产品。即使此前访问过产品 A，或列表正在筛选 A，新表单的产品仍为空。

提交成功生成一条有独立编号的反馈，状态为「待评估」。产品经理随后可以评估、直接处理、关联已有单据或转单。现场登记和决定投入研发分别留历史。

## 二、产品的需求池负责人

启用插件后，原生产品新建、编辑页面增加单人选择字段「需求池负责人」，产品详情的基本信息区显示该负责人。每个产品独立设置。由具备产品维护权限的人员配置，候选人应为账号有效且有权办理该产品反馈的成员。已有产品可在编辑页补配。

| 场景 | 用户看到的行为 |
|---|---|
| 创建反馈并选择 ERP | 表单读取 ERP 的需求池负责人，显示为本条反馈预计的当前负责人。客服和产品经理都无需再次选人。 |
| 从 ERP 切换到 WMS | 负责人、平台／分支、模块、计划等产品相关选项随之更新。保留标题、客户原话和已添加的附件。 |
| 点击提交 | 系统按最终产品读取当时有效的负责人。保存成功后，详情显示实际经办人，该反馈出现在其「待我处理」中。 |
| 产品未配置，或配置的人已停用、失权 | 仍可登记客户反馈。页面明确提示「产品待配置负责人」，暂由提报人跟进，有权人员可转交。临时跟进不增加评估或转单权限。 |
| 更换产品的需求池负责人 | 后续新件按新配置分派。已有反馈保留各自的当前负责人，确需交接时显式转交。 |

提报人回答「最初是谁登记的」，产品配置回答「新件默认分给谁」，反馈当前负责人回答「这件事现在由谁推动」。原生 Bug、需求或任务的经办人继续负责其各自的工作。

## 三、原生研发需求界面与字段

列表、新建、编辑、详情均以同版本、同主题、同配置的原生研发需求页面为原型。沿用其字段分组、控件、交互顺序、校验反馈、历史记录和详情浮动工具栏。只在需要表达客户反馈业务的位置增加字段或动作。

| 原型字段或区域 | 需求池要求 |
|---|---|
| 所属产品、平台／分支 | 保留原生选择器。普通产品、多平台产品、多分支产品按原生规则显示对应名称、主干、选项和选择方式。切换产品后重新校验依赖字段。 |
| 所属模块 | 使用原生模块树。保留根节点、父子层级、选中路径及平台／分支联动。同名子模块可通过父路径区分。 |
| 标题、类别、优先级、关键词 | 沿用原生控件、实例枚举及显示格式。类别记录需求性质；电话、群聊、客户拜访记录在采集渠道。 |
| 需求描述、验收标准 | 保留两个独立富文本编辑区，支持原生格式、粘贴图片、保存和再编辑。描述记录客户原话、场景和期望；验收标准可在评估时补充。 |
| 附件 | 保留原生附件区及适用的添加、预览、下载、移除操作。普通附件和正文内嵌图片均应在保存、编辑、重新打开后正常使用。 |
| 来源、来源备注、所属计划、预计工时、抄送给 | 按实例配置保留字段、控件和值。原生来源和客服采集渠道分别保存。 |
| 需求层级、父需求、评审、阶段与版本 | 原型允许预填的层级、父需求及评审选项可作为转单建议保存。实际评审、研发阶段和需求版本来自关联的原生需求。客户使用的产品版本单独记录。 |
| 反馈特有信息 | 增加客户／提出者、采集渠道、提报人、当前负责人、下一步、剩余事项及实际答复。客户身份暂不明确时，可保留来件线索并标为待核实。 |

开发时以安装实例逐项补全对照表。原生页面启用、上表未枚举的字段，也要记录其去向及理由。字段验收覆盖创建、保存、编辑回显、详情显示和转单带入。

### 页面

- **列表**沿用原生需求列表的筛选、列配置、勾选、排序和分页。默认突出编号、标题、所属产品、客户、状态、负责人、下一步及最近业务更新时间。提供「我提交的」和「待我处理」。地盘可直接打开分给本人的已有反馈。
- **新建／编辑**保留原生产品信息、描述、验收标准和附件分组。在相关位置增加客户信息及预计接单人。提交成功打开详情并显示反馈编号。
- **详情**沿用原生两栏布局。主栏展示描述、验收标准、附件和历史，侧栏展示基本属性、负责人及下一步。承接单据可查看实际进度。底部黑色浮动工具栏按权限和状态提供办理动作。

## 四、状态与办理

| 反馈状态 | 可执行的动作与结果 |
|---|---|
| 待评估 | 可补充、转交、评估、直接处理、转单或关联。开始办理、决定采纳或成功建立承接关系后进入跟进中。现场已解决、客户撤回等情形可直接记结果并关闭。 |
| 跟进中 | 可记录方案、沟通、转交、追加承接单和关闭。下一步写明等资料、等发布、安排复测或暂缓原因。 |
| 已关闭 | 保留结果、依据和历史。问题复发或结案错误时，可记录原因、指定负责人并重开为跟进中。 |

**直接处理。** 指导升级、修改配置或解释用法可以在反馈内办完。客户当场验证成功，负责人一次记录处理办法、实际答复并关闭。客户尚未复测，则保留跟进中。复测失败时从原反馈继续排查。

**单条转单。** 支持创建或关联 Bug、业务需求、用户需求、研发需求、执行任务。业务口径中的「客户需求」对应禅道原生「用户需求」。新建时使用对应原生表单，确认必填字段、权限及评审规则。一条反馈可以由多张单据分别承接。

**合并转需求。** 在列表勾选同产品的多条反馈，点击「合并转需求」，核对共同范围和验收标准，创建一张业务、用户或研发需求，也可关联已有需求。确认按钮显示实际结果，例如「用 3 条反馈创建 1 条研发需求」。混选产品时提示按产品分批办理。

## 五、进度回写与逐客户结案

每条承接关系都可说明本次处理范围。默认覆盖整条；只承接一部分时，原反馈保留剩余事项。每份反馈独立保留客户、原话、负责人、实际答复和结案结果。

例如甲、乙、丙都要「按仓库导出库存」，丙还要「显示审批人」。三份反馈共用一张导出需求，丙的反馈留下「审批人列待处理」。发布后，甲可以确认结案，乙可以继续等升级，丙仍有欠项。第四位客户再提导出时，可直接关联已有需求。

原生单据的状态、阶段、解决或关闭原因自动回写。负责人能看到最近核实的进展、上次实际向客户说了什么、下一步由谁做。目标取消、删除或重开时提示负责人复核。正向结案需核实剩余事项及约定的客户复测；撤回、重复、不采纳等分别记录原因。重复反馈通过选择原反馈建立关联。

## 六、首版边界

首版交付独立需求池、原生界面与字段、产品默认分派、直接办理、单条五类转单、批量三类需求、双向链接和进度回写。共同工作由原生需求承接，不增设共同主项。客户门户、飞书双向接口、自动判重、承诺审批和独立联络工作台后置。
